# CRM audit — slice `data` (prefix DT)

**Summary.** 459 inventory rows: 111 client Firestore collections/subcollections/collection groups, 4 page-level script/global rows (dashboard.html, customer.html), 11 onSnapshot listener rows, 333 Cloud Function exports. Scored cells: 593 ✅ / 45 ⚠️ / 48 ❌ (most ❌ are "no test names this function or collection"). **No client query can return another tenant's data for a normal user.** Every multi-tenant read rule in `firestore.rules` requires owner, company or parent-lead membership, so an unscoped list query gets permission-denied. It does not leak. The exception is the platform-admin role (`role=='admin'`, Jo), where an unscoped query would return all tenants. The two global feeds that do this (`alert_outbox`, `unmatched_sms`) are deliberate. The real defects are the opposite problem: queries the rules **reject**, so the panels come up silently empty.
- **DT-F01:** the saved inspection reports list (`inspection-report-engine.js:133`) uses a leadId-only query, and the rules reject it for everyone except the platform admin. The comment at `firestore.rules:3852-3855` says this query works. It does not.
- **DT-F03:** the estimate-builder and supplement photo pickers have the same leadId-only problem for sales reps and solo owners.
- **DT-F05:** Ask Joe's schedule reads appointments only through the `repUid` field, which the appointments rule never allows.
- **Unbounded reads at boot (perf):** all estimates (DT-F06), every task through a collectionGroup query (DT-F09), and the canvasser panel's whole-company knocks, leads and invoices (DT-F07).
- **Duplicate window functions:** `customer.html` defines some window functions twice. In one of them, `toggleTask`, the losing copy writes to the retired top-level `/tasks` store (DT-F10).
- **Cloud Functions:** 22 of the 333 exports have no test that names them (DT-F15). 4 audit triggers are deployed but do nothing (no-ops).

Method: static only. The helper scripts are in `C:\Users\jonat\nbd-overnight-tools\` (`fs-scan.js`, `fs-report.js`, `rules-read.js`, `page-scan.js`, `fn-scan.js`, `gen-data-md.js`). They scan 578 JS files under `docs/pro` (excluding `demo-sdk/`) and found 808 collection()/doc()/query() refs. Every flagged-unscoped hit was then checked by hand against its scope helper and against the read rule (`firestore.rules`). Emulator rules tests were **not** run, so "rules reject" is reasoned from the rule text using Firestore's rules-are-not-filters semantics.

## Section 3 — Notes

- **Rules posture:** every top-level multi-tenant collection's read rule is owner, company or parent-lead scoped (`rules-read.js` lists all 191 allow-read lines). Only `docPrefixes`, `feature_flags/_default` and `hail_mesh` allow any signed-in user. So the "unscoped and returns other tenants' data" class is empty for normal users. It applies only to the platform-admin role (DT-F13).
- **Flagged queries that are actually scoped:**
  - Through helpers: `_photoQueryScopes`, `_estimateQueryScopes`, review-handoff `photoScopes`, the dashboard `_leadScopes`/`_scopes` for leads, pins and zones, `scope` variables in d2d, mission, profit-tracker and customer-jobs, `today-plan.tasksQuery`, numbers-data `_query`, and canvasser `q()`.
  - Through the parent lead: the leadId-only `/notes` queries are valid because the notes rule does `get()` on `leads/{resource.data.leadId}` (firestore.rules:2081).
- **Rule-rejected query pattern:** a leadId-only query against a collection whose rule tests `userId`/`companyId`. Found in reports (F01), invoices (F02), and photos for non-readers (F03). Also `appointments` queried by `repUid` (F04, F05).
- **Listeners:** only 17 `onSnapshot` sites exist (11 rows here). The dashboard's hash views barely use realtime, so view-change leaks are limited to the D2D team listener (F12).
