# Speed to lead (2026-10-19)

**Why:** Thumbtack charges per lead when the customer replies, so first-response time matters. Jo answers most leads outside the CRM (texting or calling from his phone, replying inside Thumbtack or Yelp), so the CRM never learned when he responded and the Triage Inbox timer chips (red / gold / green) were wrong. It ships **dark**.

**Flag:** `speedToLead` in `feature_flags/_default` (or per user in `feature_flags/{uid}`). Absent or false = the toolbar button stays hidden, nothing is read or written. Jo flips it in the Firebase console (Claude cannot write prod flags); flags are cached up to 10 minutes. There is no flag registry to edit.

**What it does (flag on, not a viewer):**
- CRM board toolbar gets **Speed to lead** (with a count of waiting leads). The panel lists new leads (stage `new`, created in the last 7 days, no stamp), newest first. Each row has a channel menu (default from the source: Thumbtack, Yelp, else Text) and a one-tap **Replied** button.
- **Replied** stamps `leads/{id}.firstRespondedAt` (server time), `firstRespondedChannel` (`text | call | thumbtack | yelp | other`) and `firstRespondedSource: 'manual'`, in a transaction, **only if the lead is still unstamped** (null, absent and 0 all mean unstamped). **Undo** (right after) clears only a manual stamp on the same channel.
- **Call matching:** on opening the panel and once after the flags load, the module reads the user's last 300 `phone_calls` rows (filed by `functions/call-center.js`, already matched to a lead by phone) and, for each unstamped lead from the last 30 days that the user may edit, finds the earliest OUTBOUND call from the same customer (the row's `leadId`, else the phone number) that started at or after the lead was created and within 14 days of it. It stamps `firstRespondedAt` = the call's start time, channel `call`, source `call-match`, `firstRespondedCallId`, only if still unstamped (a transaction re-checks). Inbound calls and text-day rows never count. Up to 50 stamps per run.
- **Summary** (same panel): median and p90 (nearest rank) minutes to first response by lead source for leads created in the last 30 days, with an "All sources" row. **Only stamped leads are timed.** Unstamped leads are shown in their own "Not recorded" column and never enter the median or p90: a lead with no stamp is unknown, not slow. A stamp earlier than `createdAt` reads as 0 minutes.
- **Inbox:** a new lead with a stamp no longer appears as a "nobody has been in touch yet" reply-by item (`docs/pro/js/layouts/inbox.js`, one line in `buildItems`), so the red / gold / green chip stops for leads Jo has already answered. Undo (stamp back to null) puts it back.

**It sends nothing.** No text, email, call or link-out; no messaging collection, callable, function or module is touched (the test greps for it). Writes: the three `firstResponded*` fields (plus `firstRespondedCallId` for a call match) on `leads/{id}`, nothing else. Money/time: times are epoch ms, no money involved.

**Permissions:** viewers never see it. A lead is listed or matched only if the user may change it (own lead, or same company for manager / company_admin, the rule the stale-lead cleanup and `commitBulkLeadOp` use). Firestore rules need no change (`leads` update has no allow-list for these fields).

**Known limits (follow-ups, not built):** the Replied button lives in the panel, not on the inbox row (the row is itself a button); a call-match stamp has no Undo (it is a measurement, and it never overwrites a manual one); calls are matched client-side only for the signed-in user's own `phone_calls`, so a call recorded on another user's phone is not matched for them; old leads are not back-filled beyond 30 days.

**Also fixed here:** `tests/layouts-visual-audit/inbox-timer.section.js` failed whenever the sample account rendered no visible Inbox row (it only injected missing chips next to an existing row, then reported `gold: null`). It now measures real chips, seeds each missing one deterministically into a throwaway row prepended to `.ib-scroll` (exact `rowHtml`/`chipHtml` markup, scrolled into view), and skips (passes, labelled) only when there is no list to seed into. Proven it still fails: forcing the threshold to 99 fails all six checks.
