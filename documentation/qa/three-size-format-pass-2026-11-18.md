## Findings (e-sign contract PDF), for Jo to decide

1. **Not in the NBD Document Standard.** Plain Helvetica, grey and black: no navy/orange, no Montserrat/Lato, no section numbering. `CLAUDE.md` says the standard is mirrored in `functions/render-pdf.js`; this builder does not use it.
2. **Continuation pages have no running header, no page "X of Y", and the line-item table does not repeat its Description / Qty / Amount header.** On a 25-line estimate page 2 starts mid-table.
3. **Wasted space.** With 3 lines the price page is about 40 percent used, then the acceptance/signature block starts on page 2. Fine for signatures, but it lengthens paper copies.
4. Sample showed "50% deposit: 50%" (label and value repeat); check whether real `depositPlan` data does that.

A contract is legally sensitive, so pass 1 changed nothing. Findings 1 to 3 were then fixed in PR #3192 once Jo said to (layout only, no wording).

## Pass 2: the document template library (32 types), 2026-11-18

All 32 types from `NBDDocGen.DOCUMENT_TYPES` were generated by the real generator (`getHTML`, same sample homeowner and three line items for each), then rendered at 390 px (with the app's own `NBDDocPhoneLayout`, the form a phone actually shows), at 1280 px, and printed to Letter. The emulator was not needed: the generator is plain client JS. (The Firestore emulator port 8080 is held on this PC by Open WebUI, so the authed rig could not start; that was not forced.)

- **Print:** every type prints on Letter (8.5 x 11). 11 types are 1 page, 18 are 2 pages, 3 are 3 pages.
- **Desktop 1280:** no sideways overflow on any type.
- **Phone 390, still scrolled sideways after the phone layout:** `invoice` (78 px), `receipt` (78 px), `supplement_request` (82 px), `financing_options` (59 px), `company_intro` (7 px). The phone layout only covered the `.document-container` letter documents; these five use the `.doc-page` / `.letterhead` design. In the invoice, the navy header's company name overlapped the contact lines, the line-item table ran past the screen edge, and the Late Payment box was squeezed. Print of the same invoice was clean. **Fixed in PR #3195** (own file, loaded by the portal and signing pages only; see below).
- **Print spill:** `thank_you` printed 3 lines and its footer bar onto a second page. **Fixed in PR #3202** (14px / 1.4, one page).

### Correction (same day)

The first write-up said `right_to_cancel` split across two pages with the signature pad's Clear / Undo buttons printing. That was my test setup, not a defect: the render skipped `_injectSignatureAssets`, which the app always runs and which carries the widget's own `@media print` rule hiding those buttons. Rendered the way the app does it, `right_to_cancel` prints on one page with the buttons hidden. No change was needed or made.

### Loose end for Jo

`doc-phone-layout-letterhead.js` loads on `portal.html` and `sign.html` only, because the dashboard and customer-page boot-byte budgets are full. A rep viewing an invoice or receipt inside the CRM on a phone still gets the old layout. Covering that needs a budget raise (about 3 KB on each page), which is Jo's or the conductor's call. Recommendation: no raise unless reps report it; reps can open the homeowner view.

## Method

Playwright against a static server of `docs/`, with `getEstimateForView` mocked; PDFs rasterised with PyMuPDF. The e-sign PDF was built by calling `buildEstimateContractPdf` with sample data. A Playwright `page.pdf` call without margins puts text against the page edge, so margin-free output is not a finding.
